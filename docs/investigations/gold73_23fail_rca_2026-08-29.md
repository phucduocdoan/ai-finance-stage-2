# Gold73 — root-cause audit of the 23 wrong answers (v17_unitfix)

Context: `scripts/score_gold75.py --blame` on `artifacts/runs/full1012_v17_unitfix.jsonl` scores
v17_unitfix at 50/73 (68.5%) on the medium+confidence gold set. This doc is the root-cause
investigation of the 23 wrong answers, split across three sub-agents (retrieval-rca,
codegen-rca-1, codegen-rca-2), each independently cross-checking the pipeline's run trace
against the real gold in `data/eval/unbiased60_gold.jsonl` + `manual15_gold.jsonl`.

**Data-quality note surfaced during this audit**: the first draft of the trimmed audit file
(`artifacts/audits/gold73_23fail_detail.json`) mislabeled the pipeline's own predicted output as
`gold_*` fields (copied from the run's `item` field, which is a submission-shaped self-record, not
gold). It was corrected in place; the file now has real `gold_*` fields sourced from the eval
jsonl files, and the pipeline's own output under `pred_*`. All findings below were verified
against the real gold files directly, not trusted from that intermediate file.

No code has been changed yet — this is diagnosis + proposed fixes only.

## Cluster 1 — retrieval never surfaces the correct table (≈10/23: 280, 920-GVR leg, 502, 524, 744, 955, 818×5, 355)

The single largest cluster. In each case the correct table id is simply absent from
`table_ids_given_to_solver` — no amount of codegen/table-linker sophistication recovers from this.

- **355** (MSN): `understand.py`'s live LLM classifies `doc_type="separate"` with **no supporting
  keyword** in the question (in fact the question literally contains the English words "MSN 2022
  consolidated"). The offline regex classifier correctly returns "unknown" for the same question.
  `_explicit_separate_scope()` only *promotes* unknown→separate on a keyword hit; there is no
  symmetric *demotion* back to unknown when the LLM commits to a scope the question doesn't
  support. Fix: add a literal-token check (`consolidated`/`separate`/`riêng`/`hợp nhất`) before
  falling back to the LLM classifier, or demote LLM-committed scope back to unknown when no
  keyword/literal token supports it. Low risk, cheap — recommend regression run on full 73 anyway
  since this scope logic is documented as tuned against 363 questions.
- **502** (PLX) / **524** (OCB): "select year/entity by metric A (fund balance / loan volume), then
  read metric B (lãi dự thu / khen thưởng quỹ) for the winning slot" — retrieval fetches candidate
  tables for metric A across every year, but never fetches metric B's table for any year. Verified
  directly against the raw CSVs that the correct table exists in the corpus but never reaches
  `table_ids`. Fix direction: for this two-metric-select question shape, retrieval needs to fetch
  metric-B candidates for every candidate slot, not just metric-A's — an architecture-level
  retrieval change, needs care re: blast radius on other question shapes.
- **744** (EIB leg), **955** (ACB leg), **818** (FTS, all 5 years): near-duplicate note collision —
  asset-side "trái phiếu" (bonds held) retrieved instead of liability-side "trái phiếu" (bonds
  issued); a maturity-bucket table retrieved instead of the loan-term breakdown; equity/revaluation
  notes retrieved instead of the receivables-provision note. All confirmed by reading the raw CSVs.
  Same root shape as 502/524 but simpler (single-metric, wrong candidate entirely, not "second
  metric missing"). Fix direction: lexical rerank on row-label content specific to the question's
  discriminating terms ("phát hành", "ngắn hạn", "phải thu khó đòi") before or during candidate
  ranking. Do **not** revisit widening `codegen_max_tables`/multi-company caps — already measured
  to hurt (docs/config_flags.md), and these misses happen regardless of table budget since the
  correct table isn't even shortlisted.
- **280** (HDB), **920** (GVR leg): true shortlist miss, not yet traced to the exact BM25/dense/
  rerank score. `cell_locator`/`raw_table_linker` correctly abstain (fail-closed, working as
  intended) rather than guessing. Needs a follow-up: run `shortlist()`/`_fuse()`
  (`src/finance_qa/modules/rag/candidates.py`) directly against these two questions and inspect
  where the correct table ranks among same-ticker/year candidates.

## Cluster 2 — codegen's single-expression output can't represent the question's actual shape (488, 542, 526)

- **488** (AAA/DCM/DPM/GVR filter+sum), **542** (DCM/DPM/GVR filter+average): "filter N per-entity
  frames by a boolean, then sum/average a *different* metric over only the entities that pass" has
  no reliable single pandas-expression pattern in the current codegen solver. Both oscillate
  between "boolean condition, no aggregate" and "aggregate, no condition" across repair attempts.
  Needs a read of the actual codegen solver prompt/code to know whether the fix is prompt-level
  (teach the indicator-weighted-sum trick: `cond1*val1 + cond2*val2 + ...`) or requires allowing
  multi-line output instead of one inline expression.
- **526** (MWG): codegen has no argmax-then-lookup pattern — when `raw_selection_linker` correctly
  punts on a genuine data gap (2024's EPS cell is blank in-corpus), codegen's fallback hardcodes
  one year instead of comparing all 3 candidate years.

## Cluster 3 — source-table structural defects (555, 582, 663, 790, 955-partial)

- **555** (CEO): systemic OCR/extraction column-shift bug — header row has one fewer token than
  every data row (missing name for a leading STT/index column), so every column name is offset one
  column right of its real data. Confirmed identical across CEO's 2022/2023/2024 income
  statements. Codegen picked the *correct rows*; the column itself is unusable due to upstream
  extraction corruption. Recommend a corpus-wide scan (header-token-count vs data-row-token-count
  mismatch with a leading small-integer column) before fixing, to size the blast radius.
- **582** (MCH): gold wants an unlabeled reconciliation-note total row; codegen picked the literal
  phrase match ("Vay ngắn hạn" sub-line) instead. Possibly a genuine gold-curation ambiguity
  (narrow sub-line vs combined total) rather than a pure pipeline bug — worth a question to
  whoever owns gold curation.
- **663** (HAG): parent/child double-counting — summed mã330 (a subtotal) alongside mã338, one of
  mã330's own children. A "don't sum a row that's already a parent of another summed row" heuristic
  (using mã-số section-header structure) could help here specifically; treat as lower-ROI/harder
  to generalize.
- **790** (VIB) / **955** (ACB, shares the pattern): blank/unlabeled "Tổng cộng" row at the bottom
  of a bank note table — codegen picks the last *named* row instead of the real (unlabeled) total
  row directly below it. Recurs across at least two bank-note tables in this corpus. Cheap,
  contained fix: when rendering a table grid for the model, mark a trailing all-numeric row with an
  empty label as the total row explicitly (in `_grid()` / `table_context()`,
  `src/finance_qa/modules/solve/common/context.py`).

## Cluster 4 — sign-forcing bug in `between_two_companies()` (752, 759, 744-partial)

`src/finance_qa/modules/solve/codegen/execute.py:247` forces `abs()` on any two-company "chênh
lệch" (difference) money question, justified by a prior measurement that "all four labeled cases
have positive gold." Three independent, high-confidence real-gold counter-examples found this
session, all with an explicit "(A minus B, per question order)" annotation:

- **752**: ABB − MBB = −3,903,526 (pipeline computed the exact right magnitude, `abs()` flipped the
  sign).
- **759**: SCR − NVL = −3.100151474578 (same shape).
- **744**: KLB − EIB = −2,880,000 (same shape; this id also has an independent wrong-table bug, so
  fixing sign alone won't make 744 pass, but confirms the sign bug is real here too).

By contrast, percentage-point differences (790) already `abs()` correctly through their own
codegen-generated expression, so this heuristic's scope is specifically money-amount differences.
Recommendation: pull every full1012 answer where `between_two_companies()` fires (per the code's
own comment, 27 do), check sign against gold for as many as are hand-labeled, and narrow/remove
forced-abs for money differences if negative gold turns out to be common — this was added for a
measured reason, so don't blind-revert without a broader sign audit first.

## Cluster 5 — table-linker disambiguation despite correct candidate present (222, 263, 685)

- **263** (SSI): `_semantic_score` (`raw_table_linking/scoring.py:~101-115`) grants a flat n-gram
  phrase-match bonus (0.92) with **no IDF/specificity weighting** — a boilerplate 4-gram ("giá trị
  hợp lý") that appears in nearly every revaluation note outscores the one discriminating token
  (FVTPL vs AFS) that actually matters. Fix: gate the n-gram bonus on presence of a known
  Vietnamese financial-classification acronym (fvtpl/afs/htm) when the query names one; otherwise
  fall back to plain token score. Medium-high confidence, low regression risk (narrowly gated).
  Cheaper alternative worth checking first: whether table metadata already carries a
  statement-type field (balance_sheet vs income_statement) that could disambiguate a stock-vs-flow
  mismatch more cheaply.
- **222** (VIC): two independent, compounding bugs:
  1. `_STOPWORDS` (`raw_table_linking/request.py`) includes `"cho"`; stripping it collapses "cho
     vay" (to lend, asset-side) into bare "vay" (to borrow, liability-side) — two opposite-meaning
     phrases collide. Fix: remove `"cho"` from `_STOPWORDS`, or make it bigram-aware (only drop
     when not followed by vay/thuê/phép). Cheap, safe, easy to regression-test on the 73-set.
  2. Independent of the above: `cell_locator` finds the correct table (17) but two rows share an
     identical row label ("Các khoản cho vay các bên liên quan(Thuyết minh số 33.3)" at rows 1 and
     5 — short-term vs long-term, distinguished only by a section header above each, not the row
     label itself) and aborts as ambiguous rather than using `row_path`/nearest-section-header
     context to break the tie. Both bugs need fixing for 222 to pass — the stopword fix alone
     routes the question back to a table where the tie is still unresolved.
- **685** (BAB): correct denominator table (loan-quality-group breakdown) **was** among the 14
  candidates given to the solver, but the table-linker picked an unrelated balance-sheet
  liabilities table instead, matching only on the generic word "Nợ". This also requires a 3-row
  sum, which `formula_facts` explicitly declines to support — falls to ad hoc codegen, which can't
  reliably disambiguate near-duplicate "Nợ ..." tables. Fix direction: show more row-label content
  (not just header/company/year metadata) when the solver picks among final candidates, or add NPL
  coverage ratio as a supported `formula_facts` metric.

## Cluster 6 — cross-slot / multi-axis inconsistency in the selection solvers (946, 920, 530)

- **946** (NVL): `raw_selection_linker` correctly resolves 2018/2020 as consolidated, but picks
  **separate** for 2022 of the same multi-year question — no cross-slot consistency check enforces
  that all axis elements resolve to the same doc_type when the question itself gives no scope
  keyword. Fix direction (needs a follow-up code trace, exact line not yet pinned): after all
  per-slot candidates are chosen, if slots disagree on doc_type with no explicit keyword, prefer
  the majority or default-to-consolidated convention already used elsewhere.
- **920** (VIF/GVR/DPM sum): `raw_table_linker`'s own safety check
  (`raw_table_linking/validate.py:275`) catches a slot-mismatch — the decision step assigned a GVR
  candidate to what should be the DPM slot (`[VIF, GVR, DPM]` expected vs `[VIF, GVR, GVR]`
  actual). The check does its job (aborts to codegen rather than silently returning wrong data),
  but the underlying per-slot candidate-assignment bug is unresolved — not yet traced to the exact
  line in the candidate/decision-building code. Codegen's fallback then also picks wrong rows for
  both legs independently. Three failure modes stack on this one question (shortlist miss +
  slot-assignment bug + codegen row misidentification + inherent VIF gold ambiguity) — deprioritize
  fixing 920 itself, but the slot-assignment bug is worth fixing on its own merits if it recurs on
  other multi-company sum questions.
- **530** (NAB): `raw_selection_linker` produces **zero** candidates for all 5 requested year slots
  — a total candidate-generation failure, not a ranking problem. Not yet traced to a specific
  cause; hypothesis (unconfirmed) is NAB's unusually-named duplicate report directories
  (`2022_consolidated_1`/`_2`) breaking internal slot-key matching. Needs its own investigation
  session before proposing a fix. Even if fixed, NAB 2025 has 4 differently-shaped
  "Nợ đủ tiêu chuẩn" tables and only one is correct (cross-validated by the gold curator against a
  totals field) — a second, separate sibling-table ambiguity any eventual solver would still need
  to resolve.

## Cluster 7 — bugs outside the pipeline's control, or in its own self-check

- **521** (HDG): the `HDG_financial_statements_2023_consolidated` directory is a mislabeled
  duplicate of the real FY2022 report (its own OCR'd text says period-end 31/12/2022). Not
  fixable via retrieval/scoring logic — flag to whoever owns corpus/data curation. Separately (new
  finding): the pipeline's own `verify` critic step says `{"correct": true}` for this answer despite
  it being objectively wrong (500.69 vs gold 299.78) — a false negative in the self-check,
  independent of the corpus defect. Worth a look at why the critic approved a mismatched-year
  answer; this failure mode (wrong answer, high internal confidence) won't self-flag in production.
- **582** possibly also gold-curation-ambiguous (see Cluster 3).

## Methodology finding — `score_gold75.py`'s `blame()` bucketing

`blame()` only routes a wrong answer into "select_evidence/retrieve sai bảng" when there is **zero**
overlap between gold's `evidence_table_id` and `diag.evidence_tables`. This misclassifies genuine
retrieval failures as "codegen sai dòng/cột" whenever (a) only *some* of the needed tables are
missing (502: fund-balance table was retrieved, lãi-dự-thu table wasn't, so the intersection is
non-empty) or (b) gold's `evidence_table_id` is null (524, 752, 818 are `manual_solutions`/
`contaminated` rows with no structured evidence field — `want` is empty, and the check is
vacuously false, defaulting into the codegen bucket unconditionally). At least 4 of the 15
"codegen" ids (502, 524, 752, 818) are actually retrieval failures by manual verification, not
row/col mistakes. Recommend tightening the check to require full coverage and treating an empty
`want` as "unknown" rather than defaulting to codegen, so future codegen-prompt work targets bugs
that actually live in codegen.

## Prioritized fix list (safe/cheap first)

1. Fix `blame()`'s retrieval-vs-codegen attribution — pure measurement change, zero pipeline risk,
   unblocks correct prioritization going forward.
2. Remove/bigram-guard `"cho"` in `_STOPWORDS` (222, contributing cause).
3. Add a literal `consolidated`/`separate`/`riêng`/`hợp nhất` token check before the LLM doc_type
   classifier in `understand.py` (355).
4. Mark a trailing blank-labeled all-numeric row as the total row when rendering table grids for
   the model (790, 955).
5. Gate `_semantic_score`'s n-gram phrase bonus on financial-classification-acronym presence
   (fvtpl/afs/htm) (263).
6. Audit `between_two_companies()`'s forced-abs against real gold sign across all ~27 full1012
   hits, then narrow/remove for money-amount differences if negative gold is common (752, 759,
   744-partial).
7. Fix `apply_units`/`scale_expression` missing ×100 for a codegen-composed ratio expression
   targeting `percent` output (955, layered on top of its retrieval-miss fix).

Needs a follow-up code trace before proposing a fix (not yet pinned to an exact line):

8. `raw_selection_linker` cross-slot doc_type consistency check (946).
9. `raw_table_linker`'s per-slot candidate-decision step — GVR double-assigned instead of DPM
   (920).
10. `raw_selection_linker`'s candidate-generation returning zero candidates for NAB (530).
11. `shortlist()`/`_fuse()` trace for 280 and the GVR leg of 920 — why the correct table never
    ranks into the candidate pool.
12. `cell_locator`'s ambiguity tie-break using `row_path`/nearest section header when two
    candidate rows share an identical label (222, second bug).

Architecture-level, needs its own scoping before implementation:

13. Retrieval fetching metric-B candidates for every candidate slot in "select by A, read B"
    questions (502, 524).
14. Codegen support for "filter N per-entity frames by boolean, aggregate a different metric over
    the passing subset" (488, 542) and "argmax over candidates, then lookup" (526) — needs a read
    of the actual codegen solver prompt/code first to know whether this is a prompt change or an
    output-format change (single inline expression → allowed multi-line).
15. Lexical rerank on row-label content for near-duplicate note tables (asset vs liability
    "trái phiếu", maturity-bucket vs loan-term note, provision vs revaluation/equity note) — 744,
    955 (retrieval leg), 818, 685.

Not a pipeline bug — flag externally:

16. 521's mislabeled `HDG_financial_statements_2023_consolidated` directory — corpus/data owner.
17. 582's ambiguous "vay ngắn hạn" convention (narrow sub-line vs combined total) — gold curation
    owner, if not already a deliberate convention.

## Relationship to the reference slide deck

`_2026__R2AI___Stage2___Finance_Tabular_QA___Aug21 (1).pdf` was read as background before this
audit but was **not** fed to the sub-agents during the investigation — the clusters above were
derived independently from the pipeline's own trace + gold + raw CSVs. In hindsight, several
clusters map cleanly onto frameworks from that deck and may be worth revisiting through that lens
when scoping items 13-15 specifically:

- **Cluster 2 (488, 542, 526)** is a direct instance of the deck's PAL/Binder argument: a single
  inline pandas expression can't represent multi-step filter-then-aggregate or argmax-then-lookup
  logic. The deck's proposed fix (let the "Programmer" role emit a short program/plan rather than
  one expression) is a more principled reframing than patching the current codegen prompt
  case-by-case.
- **Cluster 1 (retrieval misses) and item 13-15** are the deck's TableRAG / Chain-of-Table
  argument: today's retrieval is one-shot per question; the deck's multi-hop retrieval framing
  (retrieve for the reasoning step you're on, not just the question as a whole) matches exactly
  the "select by metric A, need a table for metric B" and "same entity has both an asset-side and
  liability-side note with the same keyword" gaps found here.
- **Cluster 5 (222, 263, 685)** — near-duplicate row/table disambiguation — is the deck's
  MultiHiertt hierarchical-table-structure challenge: the fixes proposed here (acronym gating,
  row_path-aware tie-break, richer row-label context at final selection) are all instances of
  "use the table's hierarchical/positional structure, not just flat text overlap."
- **Cluster 7's `verify` false-negative (521)** relates to the deck's multi-agent
  dual-verification/reflection-loop section — the pipeline's current single critic pass has at
  least one confirmed false negative; a second, independent verifier pass (rather than one LLM
  self-check) is the deck's proposed mitigation.
- The deck's numeric-masking/de-lexicalization (FinQA) idea is a plausible complementary mitigation
  for Cluster 5's boilerplate-phrase-outscores-discriminating-token problem (263) — masking numbers
  and forcing structural reasoning would reduce reliance on the kind of surface lexical overlap that
  causes the wrong-acronym confusion — but this is a bigger architectural change than the
  narrowly-scoped acronym gate proposed in item 5, and would need its own cost/benefit case before
  pursuing over the cheaper fix.

Sandboxing/infra sections of the deck are not directly relevant to these 23 failures (no security
or infra root cause was found here — the one CUDA-OOM mention in 663's trace looks incidental, not
causal for that id's actual bug).
